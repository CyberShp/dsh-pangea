# 源码时序分析与绘制指引

本指引随产品离线提供。参考 Mermaid 社区技能的参与者、因果顺序、alt/else、loop 表达方法，输出使用当前打包的 Archify JSON 契约，不能直接输出 Mermaid。来源与固定版本见本目录 `diagram-guidance-sources.md`；外部 skill 的部署、联网、节点上限、自动更新建议不适用于本任务。

## 先建立证据，再绘消息

1. 从 context.json 中选定流程及冻结源码开始。识别参与者的真实职责，例如主机、连接接收侧、协议处理器、请求队列、完成回调。一个函数不是天然一个参与者；同职责的 helper 不拆成多个泳道。
2. 逐条确认发送方、接收方、事件/调用、触发条件、同步/异步、响应或回调、源码依据。将响应发回请求方，不能仅凭 flow.nodes 的数组顺序构造消息；线程、锁、队列、定时器之间无证据的先后关系不得强排。
3. 执行内动作（状态置位、取消未完成请求、释放连接资源）可以使用 from=to 的自消息。每个异常场景需要表达实际处理动作与最终状态，不能只在一根箭头上写 recv_fin / recv_rst / timeout 后结束。
4. 正常 FIN 不天然是缺陷或异常；RST、取消、超时、解析失败也须按当前实现判断。图表达行为，不对分支强加风险结论。
5. note 或 cards 记录消息的冻结源码位置。未知外部调用者、动态分派、运行时竞争顺序使用“待确认”说明，不能用虚线假定事实。说明这是静态源码推导或实测轨迹；静态图不能宣称已验证实际运行顺序。

## 正常与异常必须可分辨

- 互斥选择用 fragments.kind=alt，operands 分别包含条件。它们是不同场景，不能把失败消息排在成功之后冒充同一次执行。
- 重试或等待循环使用 kind=loop；唯一 operand.condition 写继续/退出条件与边界。源码未提供重试次数不得编造。
- 可选消息使用 kind=opt。当前产品不支持 par 和嵌套 fragments，不能输出这些字段。并发关系在 cards 写清已知约束与未确定顺序，必要时按一个可确认场景生成局部图，不能声称已呈现完整并发图。
- 返回消息 variant=return；异步通知 variant=dashed，并以文字说明机制。线型只表达交互语义，异常的原因、处理和结果要用明确消息及条件片段表达。
- 同一错误若共享清理过程，可在各分支引用同一职责参与者；不能因此省去影响不同的停止收包、完成请求、回收资源等必要行为。

## 结构与排版

participants 稳定 id；每条 messages 使用独立稳定 id 和真实 from/to。messages.y 表示图上顺序，不表示耗时。不要为美观伪造计时。

fragments 的 from/to 是图上纵向边界；kind 为 alt、loop、opt；operands 含 from、condition。alt 至少两个 operand，loop/opt 恰好一个。第一个 operand.from 位于 fragment.from 至少24px之后，消息离 operand.from 至少40px；else 条件与分隔线之间保持清晰。片段不重叠，不嵌套。事件过多时增大 viewBox 高度，不能删除业务消息换取排版通过。

绘制前逐场景沿真实交互核对：发起→响应/通知→状态改变→恢复/结束，明确哪里互斥、哪里循环。不能凭渲染成功判断异常覆盖充分，不能为了通过检查移动消息到错误场景。

候选由宿主校验；同一画图会话接收精确诊断后修正同一个候选。图任务不修改主 Run 的原始分析、用例、流程、状态，也不启动全仓分析。
