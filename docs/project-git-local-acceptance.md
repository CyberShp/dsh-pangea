# 项目源码与打桩：本地 Codex 全流程验收

## 版本与范围

三个仓库使用 `feature/fault-injection-e2e`。以 pangea-desktop 的 `pangea.components.json` 为最终组件锁定，禁止混用 langgraph 的插件和本分支的宿主。本次修改位于 dsh-pangea 的 companion；pangea-agent 无新增代码修改。

本轮扩展现有“添加源码仓库”入口：本地文件夹与 Git 地址两种方式。仓库配置归属当前工作区下的源码仓库；流水线 URL 为新打桩任务提供默认值，任务内可覆盖，历史任务不变。分析来源、分析源码快照、打桩任务提交各自保留。创建项目时不创建个人分支、不切换用户原仓库分支。

## 验收顺序

### 1. 普通目录创建，Git 不可用

准备含真实源码的普通目录；在隔离启动环境隐藏 Git PATH。工作台首次使用及后续“添加仓库”均选择“本地文件夹”，应成功导入并可新建分析。来源显示普通文件夹；普通分析不报 Git 依赖错误。打桩入口引导关联 Git，不自动 git init。

### 2. 已有 Git 目录与 worktree

准备完整 Git 仓库，记录当前分支、HEAD、工作区文件；制造一处未提交修改。导入后应显示分支、提交及未提交状态，副本含这处修改。原目录所有内容和分支不变。

另用 `git worktree add` 创建工作树后导入；导入副本的 `.git` 必须是独立目录，不能继续引用原 worktree 的管理目录。确认副本保留未提交修改及文件删除，原工作树不变。

### 3. 从 Git 地址创建

首次引导和后续添加入口分别测试：Git 地址、仓库名称、分析分支/标签/提交、流水线 URL。使用实际测试仓库和本机凭据。验证默认分支、非默认分支、标签对应的实际 HEAD。分析副本固定到所选提交，此时没有个人打桩分支。

错误地址、错误版本和同名仓库均需给出错误，已有项目不被覆盖；失败导入不能出现在仓库列表。验证已有仓库中含子模块或 LFS 的项目是否满足实际分析需求，记录限制，不把未拉取的内容算作已验收。

### 4. 普通目录分析后关联 Git

完成一次真实分析，在工作台或打桩区打开“代码仓库与构建”。选择对应源码仓库，关联本地 Git 根目录；另测试“克隆 Git 仓库地址”方式。保存流水线 URL。关闭重开应保留配置，原普通目录和原分析结果不被替换。

新打桩任务应使用已关联仓库和所选提交。点击“核对打桩基线”，检查分析保存的源码与 Git 提交的差异文件数和文件列表。存在未提交修改或关联仓库时，明确选择“使用所选 Git 提交作为打桩基线”；本地未提交修改不应被悄悄带入或忽略。

历史分析没有保存源码快照时只能核对 Git 状态，不应宣称源码一致。当前差异预览覆盖分析快照中的文件，不是全仓语义等价证明。

### 5. 真实分析 → 单选/多选 → 打桩 → 推送 → 构建

使用可在 Linux 构建运行的真实项目，复用 `docs/redis-linux-acceptance.md` 的场景或选择同等级项目。通过产品中的真实 ACP 执行分析与代码修改，禁止手工写好模型结果冒充生成。

分别单选和多选用例：检查任务捕获用例、固定基线、独立副本和个人分支。检查桩点开关、命中方法和原始错误处理路径，审阅实际 diff。推送到验收专用远端；从远端核对分支 SHA 等于任务记录。

测试推送途中停止、恢复、部分仓库失败后继续；不得重新生成已确认代码。生成失败时“沿用本任务配置重新生成”应创建新任务并保留旧记录。两个并行任务的源码目录及分支必须独立。

推送成功后点击“在 DSH 浏览器打开构建流水线”，必须打开配置页面。复制个人分支，在流水线选择对应分支启动构建。记录实际构建提交、制品标识，部署 Linux，逐用例验证命中与恢复，并确认不同用例的验证表单不会串写。

### 6. 配置隔离

修改项目流水线 URL：新任务使用新默认值，已创建任务保留自己的 URL。修改任务内 URL 不得改写另一任务。重启应用后仓库关联、任务记录和流水线配置仍存在；未保存草稿仅承诺当前页面生命周期保留。
