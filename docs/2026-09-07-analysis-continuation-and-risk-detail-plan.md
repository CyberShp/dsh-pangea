### 1.3 ACP 提前结束的具体链路

上一轮日志调查显示：OpenCode 自动压缩后，模型返回“继续 Step 05”的文字，但没有继续工具调用；ACP 返回本轮结束。Provider 把 `end_turn` 转成 `completed`，`settleAcpRun()` 立即返回并在 `finally` 中释放子会话，之后 `settleAcpTask()` 才发现 Run 还在 Step 05，将其结算为交付未完成。

因此，已证实的是“单轮结束被当作整个分析执行结束”，不是所有上下文压缩都会导致 OpenCode 进程自行崩溃。ACP 的 `end_turn` 只表示本次模型回答结束；客户端可以对同一会话再次发送 prompt，见 [ACP Prompt Turn 协议](https://agentclientprotocol.com/protocol/v1/prompt-turn)。

当前关键位置：

- `plugins/dsh-pangea-companion/src/workbench-api.js`：`settleAcpRun()` 的一次性等待和无条件 dispose。
- `plugins/dsh-pangea-companion/src/index.js`：`settleAcpTask()` 在 Job 结束后验证最终交付。
- Desktop 锁定的 `@deepseek-ai/dsh-subagent-acp@0.1.1-rc.2`：只调用一次 `conn.prompt()`，返回句柄没有下一轮入口。

## 2. 风险数据的统一读取设计

### 2.1 严重度只在 Reader 归一化一次

保留现有客户端枚举 `Critical / High / Medium / Low`，由 Reader 接受并归一化：

- 英文同义枚举的大小写和首尾空白，例如 `high`、`HIGH`、` High ` → `High`。
- 已有历史约定 `P0/P1/P2/P3` → `Critical/High/Medium/Low`。
- 明确的中文枚举“严重/高/中/低” → 对应四级。
- 缺失或无法识别的值 → 未分级，保留原始值供详情查看。删除缺失时默认 `Medium` 的行为。

草稿活文档路径、草稿投影路径和正式投影路径都经过同一个归一化入口。列表徽标、筛选、顶部统计、详情徽标和讨论上下文都消费该结果，前端不维护第二套猜测映射。

本次 fixture 的正确筛选数量是：**严重 0、高 2、中 8、低 1、全部 11**。这是投影现有分级的展示结果，不是对风险严重度语义的重新确认。

这个数量期望适用于带上述分级的草稿或正式投影。如果测试移除投影、只保留本次 Lua 活文档，由于 SFMEA 缺少显式风险关联，应读出 **11 条风险、11 条未分级**，六段正文仍然完整；不得为满足相同数量断言而猜测 FM↔Risk 映射。

等级来源按实际记录展示。历史数据只有投影等级时显示“来源：工作台投影”；不能统一写成“来自 SFMEA”。只有存在显式风险关联及明确分级规则时，才使用 SFMEA 的值和来源引用。`S4` 等值在没有该规则与关联时不作隐式转换。

### 2.2 按风险 ID 提取完整章节

修改 `reader.js` 的 `parseRisks()` 及相关辅助函数：

1. 支持已存在的 `R-*`、`RP-*` 标识，包括带分析单元段的 ID；保留原始 ID，并按完整 ID 与投影连接。
2. 支持真实产物中的中文/英文冒号及长破折号标题分隔。投影已给出 ID 时，以章节中明确出现的该 ID 为依据。
3. 章节截止于下一个同级或更高级标题；最后一条风险不能吞入“风险-场景-源码映射汇总”等后续章节。
4. 标签识别只清理标签位置的 bullet、加粗和箭头格式；保留正文中的代码路径、反引号、换行、后续段落和列表。
5. 同时保留该风险章节的原文及文件/章节来源。结构化字段用于直接阅读，原文用于检查遗漏；不根据标题相似度、编号尾数或源码位置猜测身份。

使用下面的有限标签映射，覆盖当前 Skill 约定、真实 Lua 产物和 DHCP 历史格式：

| 页面名称 | Reader 字段 | 可读取的正文标签 |
| --- | --- | --- |
| 风险说明 | `narrative` | 投影 `narrative` / `description`，或明确的风险概要 |
| 触发条件 | `trigger` | 条件、什么条件发生 |
| 代码失效 | `system_result` | 代码失效、代码内部哪里失效 |
| 残留状态 | `residual_effect` | 残留、状态/数据留下什么、状态/资源/数据留下什么问题 |
| 表面正常现象 | `apparent_normality` | 看似正常、为什么看似正常、为什么当前操作可能仍看似正常 |
| 对外暴露 | `external_observation` | 暴露、何时对外暴露、什么时候对外暴露 |
| 黑盒证明 | `blackbox_proof` | 黑盒证明、黑盒如何证明 |

六段因果字段分别保留；`description` 是概要，不拿来填充“代码失效”。现有残留内容也不能替代代码失效而丢掉其原本含义。

### 2.3 合并规则与来源保真

- 同一完整风险 ID 下，明确的非空投影字段优先，其余从相同 ID 的活文档字段补齐。空字符串和纯空白视为未提供，不能遮蔽已有正文。
- 概要按非空 `narrative`、`description` 归一到 `narrative`，原字段仍可保留；正文按上述独立字段合并。
- 不以一个模糊叙述覆盖另一份来源的具体因果段，不自动判断哪一份分析结论“更正确”。来源存在可机械核对的枚举冲突时，在该风险详情说明。
- 证据 ID、关联用例 ID 沿用现有显式关联并去重。共享的追溯读取函数也要接受实际 `R-*` 标识，避免风险正文修好了但用例关联仍只认 `RP-*`。
- 已有该风险原文章节但部分标签无法读取时，详情提供完整章节原文和简短的缺项提示；章节本身不存在时说明未找到对应章节，并提供实际源文件入口。
- 单条风险的缺少等级、正文缺项或来源待核对，作为该项读取提示，不升级成整个 Run 执行失败。

### 2.4 后续 Skill 发布约定

在 Agent 现有工作台投影 schema/示例及 Step 05、Step 09 约定中补齐：稳定 risk_id、规范严重度枚举、等级来源、风险说明章节引用，以及上表字段的含义。

正文继续以已写出的风险文件为依据。投影可引用明确的文件和章节，由 Reader 展开；发布时无需让 Agent 凭压缩后的记忆重新写一遍六段长文。显式的 SFMEA 关联由分析 Agent 写出，Reviewer 核对分级语义。

旧 Run 不要求重跑或修改原文件。新可选字段采用向后兼容读取；缺少字段给出定点提示。新增字段约定不引入“元数据不全就让整个 Run 失败”的门禁。

## 4. ACP 同会话续接设计

### 4.1 将一次回答与整个分析任务分开

为 ACP 运行句柄增加可选的多轮 prompt 能力，保留现有首次 `result` 的调用兼容性，并暴露原始 ACP stop reason。新能力贯通 `subagents.start()` 的实际返回链和类型声明，不依赖绕过 DSH 的私有对象访问。

ACP 层负责同一连接、进程、sessionId 的串行 prompt、输出累积和取消；不读取 PANGEA 文件。PANGEA 的 `settleAcpRun()` 在同一次 Job 内执行续接循环，在释放句柄前读取 Run 状态并决定下一步。

| 本轮结果及 Run 状态 | PANGEA 行为 |
| --- | --- |
| `end_turn`，Run 通过现有正式交付验证 | 结算成功，释放会话 |
| `end_turn`，Run 未完成、没有明确阻塞或停止请求 | 对同一 ACP 会话发续接 prompt，Job 保持运行 |
| Run 等待用户输入/审批，或连续续接没有有效进展 | 结束本次执行，任务显示“需要处理”，保留原因和当前步骤 |
| 用户取消/停止 | 取消当前轮，停止，不发下一轮 |
| refusal、传输异常、进程退出或真实执行错误 | 保留实际停止原因并结算，不自动反复调用 |
| max_tokens / max_turn_requests | 保留原始限制原因，显示需要处理；本次不隐式绕过限制 |

只有 `end_turn` 进入自动续接判断；不要靠输出中出现“compact”“继续”等关键词判断是否完成，也不在压缩事件发生时与原 prompt 并发发起请求。

### 4.2 续接内容与停止边界

- 续接前重新读取磁盘中的运行状态、当前步骤和已完成检查点，提示 Agent 以这些状态和交接文件为依据，继续执行当前步骤。压缩摘要可作为背景，不能覆盖已落盘状态。
- 沿用原 Run、源码快照、attempt、owner、Job 和 ACP sessionId；自动续接不是用户点“继续分析”的新 attempt。
- 用已完成步骤、有效检查点、约定产物内容变化判断进展。仅更新时间、日志增长、重复的“准备继续”文字不算进展；不递归扫描源码快照。
- 连续两次自动续接仍无有效进展即停止自动续接，并记录“连续续接未推进”、当前步骤和最后输出。计数在取得实际进展后归零，既有停止信号、超时及资源限制继续有效。
- 存在明确的待输入/待审批状态时等待用户处理。缺少完整等待状态的 Provider，首先保留交互请求，不自动代答；普通文本追问不会由宿主猜答案，最多在无进展边界结束。
- 释放句柄集中到整个编排结束的 `finally`，确保一次释放；下一轮前再次检查取消信号，避免用户停止后立即续发。

### 4.3 结算和可观测性

在单个分析执行中区分“本轮回答结束”“自动续接”“分析完成”“需要处理”和“执行异常”。复用现有最终交付判定，避免循环与 `settleAcpTask()` 各写一份不一致标准。

对“需要处理”的主动结束，持久化明确的分析结算原因，并映射到已有 `task.status=needs_attention`；Job 的正常结束不代表 Run 完成交付。同步修改 `settleAcpTask()`、TaskStore 和客户端派生逻辑，防止后续对账又把该原因改成“未生成正式交付”的失败。

日志记录每轮序号、原始 stop reason、续接前后步骤、进展判断和最终停止原因。历史 attempt 的错误继续保留。只有用户停止才显示“已停止”，执行异常不借用取消状态。旧 attempt 身份隔离、停止确认和续跑资格判断保留回归测试。

依赖修复通过 Desktop 现有 `patches/@deepseek-ai+dsh-subagent-acp+0.1.1-rc.2.patch` 固化，涉及公共类型/转发链时同步补齐对应版本补丁；重新安装依赖后须可复现。普通单轮调用方仍按原契约工作。
